# BF16 KV cache decode penalty on gfx1151: root cause and fix

## Summary

BF16 KV cache decode was ~20% slower than F16 on AMD RDNA3.5 (gfx1151)
despite identical memory footprint. Root cause: the flash-attention tile
kernel is FP16-only, so BF16 K/V was converted to FP16 by a full-cache
`to_fp16` pass on every flash-attention call (0.69 GB read + 0.69 GB write
per decode step at 16K context = ~5.4 ms, the exact measured gap). The tile
kernel now reads BF16 K/V natively, converting BF16 to FP16 on the
shared-memory tile load. BF16 decode went from 34.90 to 43.06 t/s on
gfx1151, at parity with F16 (42.91); cross-validated on gfx1201 (45.59 to
53.27 vs F16 53.26).

## Problem

Hardware: AMD Radeon 8060S (gfx1151, RDNA3.5), 256 GB/s shared LPDDR5X,
ROCm 7.14. Model: Qwen3.6-35B-A3B (Q8_0 weights, 41 layers, 2 KV heads,
head dim 128 = 41 KB/token -> 0.69 GB KV at 16K context). tg64 @ d16384,
no MTP, llama-benchy:

| KV type | tg (t/s) |
|---------|---------:|
| F16     | 43.09    |
| BF16    | 34.90    |
| Q8_0    | 40.83    |
| F32     | 29.54    |

BF16 has the same bytes/step as F16, so a pure bandwidth model predicts
~43 t/s for both; BF16 delivered 34.90 (-19%). Prefill is flat across KV
types (~930 t/s) and weight-bound.

## Root cause

Two findings:

1. Decode does not use the vec kernel for this model. The AMD WMMA gate
   (`Q->ne[1] * gqa_ratio_eff > 8`) fails at decode batch 1 (1 x 8 > 8 is
   false), and the VEC gate requires `K->ne[1] % 256 == 0`, which decode
   never satisfies. Everything - decode, prefill, MTP verification - runs
   the generic TILE kernel (confirmed with a debug print).
2. The TILE kernel is FP16-only. `launch_fattn` (fattn-common.cuh) runs
   `to_fp16` over the entire K and V tensors on every flash-attention call
   when `need_f16_K/V` is set. For BF16 KV at d16384 that is 0.69 GB read
   + 0.69 GB write per decode step = ~5.4 ms = the exact measured gap. The
   same mechanism explains Q8_0 KV (40.83 instead of a bandwidth-bound ~55)
   and F32 KV (29.54).

The attention math was never the bottleneck. The emulated-BF16
`vec_dot_fattn_vec_KQ_bf16` (upstream FIXME) only runs in the vec kernel,
which this model's decode never selects. See docs/backend/HIP.md for the
kernel-selection and ISA background.

## Fix

The tile kernel is now native-BF16 end-to-end (AMD RDNA3/3.5/4, guarded by
V_DOT2_F32_BF16_AVAILABLE with explicit __gfxXXXX__ arch macros - the
RDNA3/RDNA4 compiler macros are never defined for gfx1151):

- K/V tiles stay BF16 (no conversion at load, no DRAM round-trip).
- Q converted to BF16 once at fill.
- QK^T via v_dot2_f32_bf16 (exact BF16 products, FP32 accumulation).
- P stays FP32, PV runs FP32 math with FP32 accumulation.

This preserves the full BF16 exponent range through every attention op and
removes the FP16 saturation at deep context (the inference-loop symptom).
The FP16 PV accumulation bug (half2 VKQ) that affected all KV types is also
fixed. DV > 256 (rare 512/576-head models) and non-AMD platforms keep the
FP16-conversion tile path.

Packed PV opt-in: GGML_HIP_BF16_PV_DOT2=1 rounds P to BF16 and computes the
PV with v_dot2_f32_bf16 (V rows paired across consecutive KV rows via
v_perm_b32, one dot2 per head pair, FP32 accumulation). This recovers the
last ~3% at deep context (exact F16 parity) at the cost of P at 7-bit
mantissa instead of FP32. FP32 PV is the default.

## Results

no-MTP decode (deterministic llama-cli harness, fixed prompt + temp 0 + seed):

| KV type | short ctx | d16384 (benchy) |
|---------|----------:|----------------:|
| F16     | 48.0      | 42.95           |
| BF16 native, FP32 PV (default) | 47.9 | 41.72 |
| BF16 native, packed PV (GGML_HIP_BF16_PV_DOT2=1) | 47.8 | 42.90 |

MTP (draft-mtp, n-max 3, temp 0): BF16 default 78.3, packed 79.5 t/s.
F16/Q8_0/F32 paths are unregressed; generation is coherent in both PV
modes. Benchmark numbers are the post-fix state (pre-fix BF16 was 34.90
@ d16384).

Cross-validated on gfx1201 (RDNA4, Qwen3.5-9B, tg64 @ d16384, no MTP):

| KV type | before | after |
|---------|-------:|------:|
| F16     | 53.26  | (unaffected) |
| BF16    | 45.59  | 53.27 |

Same ~14% BF16 penalty pre-fix, exact parity post-fix.

## Validation

- Deterministic harness (llama-cli, fixed prompt file + temp 0 + fixed
  seed): bit-identical token streams across runs, timing noise ~0.5%.
  Command: `llama-cli --single-turn -f <prompt> --temp 0 -s 12345 -n 128
  --no-display-prompt -fa on -ctk bf16 -ctv bf16`. Use temp 0 for MTP
  acceptance comparisons - at temp > 0 the two PV modes take different
  sampling trajectories and the rates are not comparable.
- F16/Q8_0/F32 paths unregressed; generation is coherent in both PV modes.
- MTP (draft-mtp, draft-n-max 3, p-min 0.50): BF16 default 78.3 vs packed
  79.5 t/s (temp 0). The earlier apparent MTP gap (53.78 vs 62.62,
  llama-benchy) was random-prefill acceptance variance, not a kernel
  defect.

## Deferred

- VEC path native QK^T dot (`v_dot2_f32_bf16` with Q pre-converted to
  BF16): kept out of this change because it changes Q precision (FP16 ->
  BF16) and does not affect this model's decode path (VEC is never
  selected during decode on this hardware). Only relevant for models where
  decode selects VEC (no-GQA, ALiBi, unpadded KV lengths).
- MMA BF16 instances: the WMMA gate cannot fire during decode or MTP
  verification on this hardware (requires KV length multiple of 256; no KV
  cache padding in the tree), so they would be dead code. Revisit if KV
  cache padding lands upstream.
